# A-131 (11-15): dialogue options, folk side

Issue #25 (conversation), follows A-129 (PR #416). Lane: folk, branch folk/dialogue-options from main.
Design: docs/design/dialogue-options.md (on main). Shares (rule 33): one choice system. The default Accept/Decline
pair becomes the first options list, not a second path.

## Row 1: data and API (no UI)
- Lines take an optional `options` list (say, then, do; 1-4 options) in dialogue.json, parsed and validated by
  LiveJsonFile with bad entries named.
- `Answer.Options`, plus `FolkConversation.Choose(index)`, which follows `then` to the next line and runs `do` from a
  list of known actions only. A `do` that changes host state (pay, give) is a rule 11 ask first.
- Tests: parse, a bad entry rejected, a Choose chain, and the Accept/Decline default unchanged.

## Row 2: three sample conversations
- A hermit, an innkeeper and a guard each get one branching exchange in dialogue.json, reached via the existing
  conversation API. Check: walk the branches in a test.

The player UI (FolkTalk shows options on keys 1-4) is a follow-up player card. Nothing new goes over the network.
